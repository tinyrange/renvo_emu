A deterministic core for embedded systems.

A Rust-based, interpreter-first microcontroller emulation framework for six initial microcontrollers, built to distil compiler and firmware samples into small, reproducible tests—with functional peripherals, external stimulus, and VCD output.

01

Project brief

Renvo is a deterministic, scriptable embedded-system simulation platform. Its first job is to run compiler-produced bare-metal programs predictably across CH32V006, CH32V003, RP2040, RP2350, ESP32-S3, and ESP32-C6; compare their observable behaviour; and reduce failures to durable regression tests. The first baseline is useful firmware execution, not exhaustive peripheral or radio emulation.
First killer use case

Compiler corpus distillation

Compile existing samples across toolchains and flags, execute them under controlled conditions, detect divergence, and preserve minimal reproducers.

Execution
Interpreted only. No JIT in the initial design.
Fidelity
Architecturally correct CPU behaviour and functionally useful peripherals; approximate, deterministic timing.
Initial ISA
QingKe RV32E, standard/extended RV32IMAC, Armv6-M, Armv8-M, and Xtensa LX7 profiles required by the six chips.
Initial machine
Six named chip models, each satisfying the same baseline contract; synthetic machines remain internal CPU test harnesses.
Observability
Structured events internally; VCD is the first trace exporter, not a dependency of device models.
Boot strategy
Direct ELF loading first for compiler tests, then vendor-image boot compatibility where it is needed by SDK samples.
Target gate
A chip counts as baseline-supported only when it boots representative compiled samples and passes the shared acceptance suite.
02

Scope boundaries

Build now

A useful vertical slice

  • The CPU profiles required by all six named microcontrollers
  • ELF loading, symbols, chip memory maps, flash windows, and MMIO
  • Deterministic scheduler and explicit stop conditions
  • Reset/clock controls, GPIO, timers, UART, interrupts, and external pin stimulus
  • Typed signal events and standards-compliant VCD export
  • CLI-driven test cases and compiler build matrices
  • Run artifacts suitable for comparison and reduction
Deliberately later

Preserve room; do not implement yet

  • Cycle-accurate pipelines, caches, or bus contention
  • JIT or dynamic binary translation
  • Analog simulation, RF, or transistor-level behaviour
  • Wireless PHY/MAC stacks, comprehensive USB, or every vendor peripheral
  • GUI-first workflows or a custom IDE
  • Full-system Linux, MMUs, or application processors
  • Precise video/audio and complete retro machines
Meaning of “wide range”

The first release deliberately covers six chips, but each has an explicit baseline rather than a claim of full-silicon compatibility. The framework is successful when shared CPU, bus, signal, and device behaviour supports those models without six monolithic implementations.

Six initial target chips

“Baseline support” is the same promise on every target: load a normal compiler-produced ELF, establish a documented reset or direct-load state, execute the application CPU, handle traps and interrupts, expose GPIO in VCD, provide a working timer and UART, and terminate deterministically. Extra peripherals are selected for SDK usefulness.

Scope note: radios and secondary cores

Wi-Fi, Bluetooth LE, and 802.15.4 are outside the first baseline. ESP32-S3 starts in ESP-IDF unicore mode; ESP32-C6’s LP core and the second RP core are parked with their documented wake/launch registers modelled. Multicore scheduling comes after every primary core passes Tier 1.

WCH reuse opportunity

CH32V003 and CH32V006 share the QingKe V2/RV32E lineage and several familiar WCH peripheral concepts, making them a useful early test of CPU profiles and reusable device logic. Their V2A/V2C core revisions, memory capacities, interrupt details, and peripheral registers must still be verified independently rather than aliased wholesale.

Ownership rule

CPU crates know about architectural state, interrupt inputs, and a bus contract. Device crates know about registers, scheduled events, and signal ports. Neither knows about Starlark, VCD text, the CLI, or a particular board.

Device-specific glue owns reset values, IRQ assignments, clock hookups, and address maps. This is where unavoidable vendor variation belongs. 

pub trait Cpu {
    fn reset(&mut self, kind: ResetKind);
    fn step(&mut self, bus: &mut dyn Bus, now: SimTime)
        -> Result<StepOutcome, CpuFault>;
    fn inspect(&self) -> &dyn CpuInspection;
}

pub struct StepOutcome {
    pub elapsed: SimDuration,
    pub reason: StepReason,
}

pub trait TraceSink {
    fn declare(&mut self, signal: &SignalDescriptor);
    fn change(&mut self, at: SimTime, event: &SignalChange);
}
05

Time, pins, and waveforms

Time model

Approximate, never ambiguous

Every CPU step advances monotonic simulation time. Initial instructions may use a simple fixed or table-driven cost; devices schedule events on the same timeline.

Ordering

Stable tie-breaking

Events at the same timestamp are ordered by deterministic sequence number. Runs with the same machine, firmware, inputs, seed, and limits must produce identical results.

Fidelity metadata

Say what is approximate

Each machine and device declares its fidelity: architectural, functional, or educational. VCD metadata records the machine, time model, and emulator version.

Digital signal model
  • Four-state values: 0, 1, Z, and X
  • Ports have direction, width, drive mode, and optional pull state
  • Nets resolve multiple drivers and report contention
  • External stimuli use the same scheduled event path as devices
  • Edges can trigger assertions, interrupts, protocol models, and stop conditions
VCD contract
  • VCD generation subscribes to structured signal-change events
  • Names are hierarchical: board.mcu.gpioa.pin5
  • Only value changes are emitted; identical writes are suppressed
  • Timescale is explicit and configurable per machine
  • Register and instruction traces remain separate from pin waveforms
Important contract

“Not cycle accurate” means timing may not match silicon. It does not mean events can occur without an order, a duration, or a documented relationship to simulation time.

Compiler and sample distillation

Treat the corpus as a repeatable pipeline, not a directory of binaries. Every result must retain enough provenance to rebuild it, compare it, and reduce it.

IngestSamples + metadata
Build matrixTools × flags × targets
ExecuteControlled machine state
CompareOracles + trace digests
ReduceSource, flags, inputs
PreserveMinimal regression
Case manifest records
  • Source origin, revision, and applicable licence
  • Compiler identity, full version, target, flags, linker script
  • Runtime libraries and hashes of all build inputs
  • Machine definition, initial memory, stimuli, and random seed
  • Stop conditions, expected outputs, and comparison policy
  • Emulator version and run artifact schema version
Observable results
  • Termination reason, exit convention, and architectural fault
  • Selected register values and named memory regions
  • UART/semihosting output and peripheral assertions
  • GPIO edges, VCD, and contention diagnostics
  • Instruction count, virtual time, and coverage bitmap
  • Canonical event digest for quick equivalence checks
Comparison mode Use Caution
Known answer Compare a run with explicit expected memory, output, signals, or faults. Best oracle; requires trustworthy expectations.
Cross-compiler Compile defined programs with GCC, LLVM, Rust, Zig, or vendor tools and compare outcomes. Only valid for defined source behaviour and equivalent runtime assumptions.
Reference engine Compare final state or bounded step traces with another ISA implementation. Normalize implementation-specific timing and environment details.
Metamorphic Apply semantics-preserving source, input, or build transformations. Transformations themselves need independent validation.
Hardware capture Replay stimuli and compare coarse outputs against a physical board. Use tolerances; functional timing is not silicon timing.
Reduction order

First remove build variants and machine inputs, then reduce source, and finally reduce the linked binary or execution prefix. A candidate is accepted only when it preserves the same divergence signature across repeated deterministic runs. 

# tests/compiler/crc.star
case = compiler_test(
    source = "samples/crc.c",
    compilers = [
        gcc(opt = "0"),
        gcc(opt = "2"),
        clang(opt = "2"),
    ],
)

results = run_all(
    case,
    machines = ["ch32v003", "ch32v006", "esp32c6", "rp2350-hazard3"],
    until = any_of(exit(), fault(), timeout(instructions = 100_000)),
)

assert_equivalent(
    results,
    compare = ["exit_code", "memory:result", "exceptions"],
)

Primary risks and controls

Risk Control Signal to watch
Target sprawl Freeze the first portfolio at the six named chips; enforce Tier 0/Tier 1 acceptance before deeper peripherals. A single SDK sample drives a large peripheral detour before the shared baseline passes.
WCH near-match assumptions Profile QingKe V2A and V2C separately and verify each reused peripheral register against its own reference manual. CH32V003 firmware passes only because CH32V006 reset values or interrupt behaviour were copied across.
Four CPU families at once Use separate CPU crates and conformance suites with a narrow shared step/bus/interrupt contract. Architecture-specific state leaks into the scheduler or generic bus API.
Multicore nondeterminism Start with secondary cores parked, then use deterministic round-robin quanta and explicit same-time ordering. Test results depend on host threads, wall time, or hash-map iteration.
SDK dependence on mask ROM Keep direct ELF mode independent; implement sourced boot ROM code where available and narrow, versioned ROM-call façades elsewhere. A vendor SDK update calls an unmodelled ROM address or depends on undocumented boot state.
Xtensa conformance gaps Define the implemented LX7/compiler subset from emitted binaries, official Espressif material, toolchain tests, and differential execution. Valid ESP-IDF output reaches instructions whose semantics have no independent test oracle.
False compiler bugs Reject undefined source behaviour; compare runtime/ABI assumptions; confirm with an independent oracle. Divergence disappears with sanitisation or a reduced optimisation level.
Peripheral abstraction leakage Keep vendor glue in chip definitions; reuse behaviour only when register semantics actually agree. Generic device traits accumulate vendor-named methods.
Fake timing becomes an API promise Record fidelity, keep SimDuration extensible, and separate event order from wall-clock claims. Tests rely on undocumented instruction timing constants.
Trace volume dominates execution Filtered subscriptions, streaming sinks, event digests, bounded buffers, optional detailed traces. Default runs allocate per instruction or retain unbounded history.
Corpus cannot be redistributed Track origin/licence at ingestion; support recipes and patches when source cannot be vendored. A test has no source revision or clear redistribution status.
Scripting controls the kernel design Expose stable Rust APIs first; Starlark wraps machine/test operations and never owns simulation state. Core types contain interpreter values or callbacks.

Six-chip baseline definition

  • Runs compiler-produced ELFs for every documented target CPU profile.
  • Implements target memory maps, reset state, architectural traps, and interrupt entry.
  • Provides deterministic flash/RAM/MMIO, timer, GPIO, UART, and interrupt routing per chip.
  • Accepts scheduled external pin inputs and resolves digital nets.
  • Emits valid VCD with stable hierarchical signal names.
  • Stops on exit, fault, breakpoint, signal edge, virtual time, or instruction budget.
  • Produces a stable machine-readable run result and canonical event digest.
  • Runs selected WCH EVT, Pico SDK, and ESP-IDF samples without source patches to peripheral code.
  • Builds freestanding cases across applicable GCC, LLVM/Clang, and Rust toolchains and optimisation levels.
  • Compares selected output state and flags behavioural divergence.
  • Reduces a seeded divergence on RISC-V, Arm, and Xtensa and saves reproducible regressions.
  • Publishes per-chip register coverage, fidelity, unsupported behaviour, provenance, and licences.
  • Demonstrates identical results across repeated runs and supported host platforms.
  • Leaves CPU, devices, tracing, scripting, and CLI concerns in separate crate boundaries.
Portfolio completion rule

All six targets are confirmed and can proceed from public vendor documentation. Portfolio completion still means six independently passing Tier 1 baselines—not one generic RISC-V model, one generic Arm model, or borrowed register maps presented under several chip names.
