Follow-on implementation plan · 1 August 2026

Seven more MCUs.
Seven distinct machines.

Extend Renvo with ATSAMD21E18, STM32L432KC, R7FA4M1AB3CFM, ATmega328PB, MSP430FR2433, PIC16F15376 and EFM8BB52F32G. The outcome is a deterministic compiler and firmware baseline for each part—not a claim of complete peripheral or cycle-accurate emulation.

01

Intent

Objective

Prove Renvo beyond its original CPU families

Add three new Arm machines plus AVR8, MSP430X CPUXv2, enhanced mid-range PIC16 and MCS-51 interpreters. Begin by splitting the current oversized implementation files without changing behaviour, then run compiler-produced firmware through reset, interrupts and a useful peripheral slice while retaining deterministic results, external stimulus and VCD.

Definition of useful

Enough hardware for real small programs

Each target must support C startup, native ABI code, GPIO, a timer interrupt, UART, and at least one vendor example. Unsupported registers must be reported honestly; they must not silently behave like successful hardware accesses.

Ordering principle

Deliver one independently passing vertical slice before starting the next architecture: ATSAMD21E18 → STM32L432KC → R7FA4M1AB3CFM → ATmega328PB → MSP430FR2433 → PIC16F15376 → EFM8BB52F32G.

02

Scope boundary

In scope

  • Seven exact chip identities and documented memory maps.
  • Compiler-emitted CPU instructions required by the qualification corpus.
  • Architectural reset, traps, interrupts and low-power wait/wake used by tests.
  • Flash/program memory, SRAM/data memory and required nonvolatile state.
  • Clock-control register behaviour sufficient for selected firmware.
  • GPIO, external pin stimulus, one timer and one UART per target.
  • Streaming VCD and the existing structured run-result contract.
  • Offline, digest-pinned Docker compilation after image construction.
  • ELF and Intel HEX loading where the vendor toolchain requires them.
  • Behaviour-preserving decomposition of current oversized Rust source files.

Explicitly out of scope

  • Cycle-, pipeline-, flash-wait-state- or power-accurate simulation.
  • JIT compilation or native-code translation.
  • Every peripheral, pin package or derivative in each MCU family.
  • USB, CAN, advanced analog fidelity, radio, motor-control and display stacks.
  • Full debug-probe emulation or production-programmer protocols.
  • Electrical voltage/current modelling beyond resolved digital logic.
  • Undocumented silicon quirks unless a selected test demonstrably needs one.
  • Additional MCUs discovered while implementing these seven.
  • The UNO R4 WiFi ESP32-S3 coprocessor, radio stack and RA↔ESP bridge protocol.
  • Hardware-in-the-loop as a completion requirement; it remains optional validation.
03

Refactoring comes first

Phase-zero rule

No new MCU implementation begins until the current hotspots are split into cohesive modules and the existing qualification results remain unchanged. This is structural work, not permission to redesign working behaviour or expand abstractions speculatively.

Module policy

  • lib.rs and main.rs primarily declare modules, re-export APIs and perform top-level wiring.
  • Prefer cohesive production modules around 300–800 lines.
  • Review any production module approaching 1,000 lines.
  • No production Rust source file may exceed 1,500 lines when phase zero closes.
  • Keep architecture-neutral contracts free of vendor-specific conditionals.
  • Preserve named register enums and stable public re-exports.

Behaviour-preservation gate

  • No CLI syntax, public Rust API or serialized artifact-schema change.
  • Existing unit, integration, corpus, firmware and documentation gates pass.
  • Golden run results, bus logs, VCD traces and event digests remain identical.
  • Moves are performed crate by crate in reviewable patches.
  • Compatibility re-exports protect downstream crates during decomposition.
  • New abstractions require an immediate current use; file movement alone is sufficient.
04

Target baselines

ATSAMD21E1801 · Arm

Cortex-M0+, up to 48 MHz, 256 KiB Flash and 32 KiB SRAM; the E18A device/package definition is the initial manifest.

CPU and system

  • Reuse and extend the existing named CortexM0Plus profile.
  • Vector-table reset, NVIC, SysTick, faults and exception return.
  • Flash aliasing, SRAM map, synchronization flags and documented reset state.
  • Arm EABI qualification with the existing GCC and Clang lanes.

Peripheral slice

PM, SYSCTRL, GCLK, NVMCTRL startup surface, PORT, EIC, TC3, SERCOM0 USART and watchdog. Pin multiplexing is modelled for the selected E-package pins.

Proof firmware

Freestanding corpus plus selected Microchip SAM D21 GCC/Harmony GPIO, SysTick or TC, EIC and SERCOM USART examples configured for the E18 device.

STM32L432KC02 · Arm

Cortex-M4F, up to 80 MHz, 256 KiB Flash and 64 KiB SRAM.

CPU and system

  • Named CortexM4F profile; do not alias Cortex-M33.
  • Compiler-used Thumb-2, DSP and FPv4-SP-D16 instructions.
  • Vector-table reset, NVIC, SysTick, faults and exception return.
  • Soft, softfp and hard-float ABI qualification.

Peripheral slice

RCC, FLASH/PWR startup registers, GPIO A/B/C/H, SYSCFG/EXTI, TIM2 and USART2.

Proof firmware

Freestanding corpus plus selected STM32CubeL4 LL/HAL GPIO, timer-interrupt and UART examples.

R7FA4M1AB3CFM03 · Arm

Renesas RA4M1 Cortex-M4F at up to 48 MHz, with 256 KiB code Flash, 32 KiB SRAM and 8 KiB data Flash; the exact #AA0 device used by UNO R4 is the initial manifest.

CPU and system

  • Reuse the named CortexM4F profile established by STM32L432KC.
  • Armv7E-M Thumb-2/DSP, FPv4-SP-D16, NVIC, SysTick and exception return.
  • Renesas option-setting memory, reset state, write protection and flash/SRAM maps.
  • ICU event-to-NVIC routing represented explicitly rather than as STM32-style EXTI.

Peripheral slice

SYSTEM clock/oscillator control, module-stop registers, IOPORT, ICU, GPT0, SCI9 UART and watchdog, including the pin configuration used by the UNO R4 variant.

Proof firmware

Freestanding GCC/Clang corpus, selected Renesas FSP GPIO/GPT/SCI examples, and pinned ArduinoCore-renesas Blink plus HardwareSerial sketches without USB or Wi-Fi as an oracle.

ATmega328PB04 · AVR8

8-bit AVR, 32 KiB Flash, 2 KiB SRAM, 1 KiB EEPROM and 32 working registers.

CPU and system

  • AVR instruction decoder, SREG flags and word-addressed program counter.
  • Harvard program/data/I/O spaces and program-memory reads.
  • Stack, reset/interrupt vectors, sleep and watchdog reset path.
  • PB identity retained; no ATmega328P register-map shortcut.

Peripheral slice

Clock prescaler/power reduction, PORT B/C/D, external and pin-change interrupts, Timer0/1, USART0, EEPROM and watchdog.

Proof firmware

AVR-GCC corpus and selected Microchip device-pack or avr-libc examples, including interrupt-driven UART or timer code.

MSP430FR243305 · MSP430X

16-bit CPUXv2, 20-bit address space, FRAM program storage and 4 KiB SRAM.

CPU and system

  • Classic and extended MSP430X encodings and addressing modes.
  • Twenty-bit registers/addresses, constant generator and status flags.
  • Reset vector, interrupt entry/return and low-power-mode wake.
  • Unified memory semantics with persistent FRAM snapshots.

Peripheral slice

Clock System, FRAM controller, PMM startup surface, WDT_A, GPIO, Timer_A and eUSCI_A0 UART.

Proof firmware

MSP430-GCC corpus plus selected TI register-level examples for GPIO, Timer_A and eUSCI.

PIC16F1537606 · PIC16

Enhanced mid-range 8-bit core, 16K × 14-bit program words, 2 KiB RAM and a 16-level hardware stack.

CPU and system

  • All 49 enhanced mid-range instructions and skip timing/order.
  • WREG, STATUS, BSR, FSR/INDF, banked data and common RAM.
  • Word-addressed program memory, reset/interrupt vectors and return stack.
  • XC8 startup conventions and Intel HEX program-word reconstruction.

Peripheral slice

Oscillator control, PORT/LAT/TRIS/ANSEL, PPS, PIR/PIE interrupt routing, Timer0/1, EUSART and watchdog.

Proof firmware

XC8 corpus plus selected Microchip register-level or MCC-generated GPIO, timer and EUSART examples.

EFM8BB52F32G-QFN3207 · MCS-51

Modern pipelined 8051-compatible core at up to 50 MHz, with 32 KiB Flash, 2.30 KiB RAM and 29 GPIOs.

CPU and system

  • Complete base MCS-51 instruction semantics with EFM8 interrupt behaviour.
  • Named accumulator, B, PSW, SP, DPTR, PC and register-bank identities.
  • Separate CODE, IDATA, XDATA, SFR and bit-addressable spaces.
  • SDCC calling conventions and supported 8051 C memory models.

Peripheral slice

Reset/clock control, watchdog, Ports 0–3, priority crossbar, Timer 0/2, UART0 and interrupt enable/priority routing.

Proof firmware

SDCC compiler corpus plus a selected Silicon Labs GPIO, timer and UART example, adapting only compiler declarations or board pin bindings when necessary.

Retro-computing seam

The MCS-51 interpreter is architecture-only; EFM8 clocks, crossbar and peripherals stay in the machine layer. This deliberately leaves the CPU reusable for older 8051-family systems later, while bank switching, precise historical timing and complete retro machines remain outside this tranche.

Containerized toolchains

Renvo continues to invoke no host firmware compiler. Image construction may download a vendor archive and device pack; case compilation is offline with a read-only root, --network=none, --pull=never, resource limits and an immutable image ID.

Provenance rule

Each image records vendor URL, version, archive SHA-256, device-pack version, Dockerfile hash and final image ID. Vendor terms are reviewed before publishing an image; where redistribution is not permitted, the repository supplies a reproducible local build recipe.

07

Implementation sequence

PHASE 0

Behaviour-preserving decomposition

Split the measured source hotspots into cohesive modules, retain compatibility re-exports, enforce the 1,500-line ceiling and prove that existing run results, traces, artifacts and gates are unchanged.

PHASE 1

Evidence and executable specifications

Pin vendor manuals, errata, linker maps, ABI documentation, compiler versions and sample revisions. Add a manifest for every target before adding target code.

PHASE 2

Shared image and architecture plumbing

Add typed architecture identities, strict Intel HEX support, non-32-bit snapshots, named register enums and address-space tests without regressing the original six targets.

PHASE 3

ATSAMD21E18 vertical slice

Reuse the Cortex-M0+ interpreter, implement the SAM D21 clocks, synchronized registers, PORT/EIC, TC and SERCOM slice, then pass freestanding GCC/Clang cases and selected official examples.

PHASE 4

STM32L432KC vertical slice

Implement Cortex-M4F compiler coverage, system exceptions and the selected L4 peripherals. Pass freestanding GCC/Clang cases and selected STM32CubeL4 examples before moving on.

PHASE 5

R7FA4M1AB3CFM vertical slice

Reuse Cortex-M4F, implement RA4M1 option/reset/clock, ICU, IOPORT, GPT and SCI behaviour, then qualify FSP examples and pinned ArduinoCore-renesas sketches for the UNO R4 device.

PHASE 6

ATmega328PB vertical slice

Implement AVR execution and Harvard memory, then GPIO, timer, USART, EEPROM and interrupts. Validate native 16-bit-int C behaviour and PB-specific register definitions.

PHASE 7

MSP430FR2433 vertical slice

Implement CPUXv2, extended addressing and unified FRAM, followed by clocks, WDT_A, GPIO, Timer_A and eUSCI. Include low-power wake and persistent FRAM tests.

PHASE 8

PIC16F15376 vertical slice

Implement enhanced mid-range execution, banked data and word-addressed images, then PPS, GPIO, timers, EUSART and interrupt routing. Qualify XC8 startup and generated code.

PHASE 9

EFM8BB52F32G vertical slice

Implement the reusable MCS-51 interpreter and split memory spaces, then add EFM8 clock/reset, GPIO crossbar, timers, UART and interrupts. Qualify SDCC memory models and selected Silicon Labs examples.

PHASE 10

Cross-target hardening

Run the complete seven-chip matrix, reduce divergences, verify VCD determinism, publish coverage/fidelity reports and keep the fast pull-request gate below 60 seconds.

08

Qualification strategy

ISA

Decode and semantics

Table-driven instruction vectors, flags, addressing, stack, reset, interrupt entry/return, illegal encodings and boundary addresses.

Compiler

Real generated code

Startup, ABI calls, recursion, switch lowering, shifts, multiply/divide helpers, aggregates, volatile MMIO and optimization-sensitive control flow.

Machine

Observable firmware

Timer IRQ drives a pin, external edge changes state, UART reports results, VCD records transitions and repeated runs produce identical digests.

C corpus lanes

LanePurposeOracle
Portable fixed-widthRun the same defined-behaviour cases using uint8_t, uint16_t, uint32_t and explicit serialization.Host-calibrated expected bytes independent of target int width.
Native ABIExercise each compiler’s real char, int, pointer, enum, struct and calling conventions.Per-toolchain expectations derived from standards, ABI documents and inspected output.
MMIO and interruptsExercise volatile accesses, read/modify/write, ISR prologues, nested calls and sleep/wake.Expected memory, UART, interrupt counts and ordered signal edges.
Vendor sampleCompile a selected official example with unchanged peripheral source logic.Documented UART/GPIO/timer outcome and trace assertions.

Standard optimization flags are used where the compiler supports them; XC8 equivalents are recorded rather than pretending every vendor compiler accepts GCC’s flag vocabulary.

CI split

Fast gate · required

Under 60 seconds on the calibrated host: Rust tests, loader tests, focused ISA vectors, one compiler smoke case and one peripheral/VCD scenario per new target.

Full matrix · scheduled

All corpus cases, compiler/optimization lanes, vendor samples, determinism repetitions, artifact inspection and coverage reports. Failures are reduced and promoted into the fast gate.

Available-board correlation

Because development boards are available, selected qualification firmware should also run on the corresponding physical board. Record the exact board revision, MCU marking, tool used to flash it, UART output and captured pin timing, then compare logical edge order with Renvo. Hardware correlation strengthens the evidence but does not turn this tranche into a cycle-accuracy project or block completion when board automation is absent.

  1. Refactored current crates with cohesive modules, thin entry files, compatibility re-exports and unchanged qualification artifacts.
  2. Seven target manifests with exact memory maps, CPU profile, vectors, pins, interrupt lines, reset assumptions, evidence links and fidelity tier.
  3. Seven runnable machine targets exposed consistently through the CLI and library APIs.
  4. Four new CPU crates and one new Arm profile with named register enums, snapshots, structured faults and unit vectors.
  5. Firmware loaders for the ELF identities and Intel HEX/program-word layouts required by the selected toolchains.
  6. Seven pinned toolchain specifications using the shared Arm recipes or target-specific recipes, all offline during case compilation.
  7. Peripheral models sufficient for each target’s reset, GPIO, external input, timer interrupt and UART scenario.

  9. Selected vendor samples with source revision, licence, build recipe, expected outcome and any non-peripheral harness adaptation documented.
  10. Documentation showing implemented register coverage, unsupported behaviour, compiler versions, run commands and known deviations per chip.

Risks and controls

STM32 appears reusable but exposes missing M4F behaviourCreate a distinct profile, qualify Thumb-2/DSP/FPU output, and never route it through the M33 identity.Firmware passes only with soft-float or disabled optimization despite using a hardware-FPU ABI.

11

Final acceptance

GATE 01

Structural baseline

The named current hotspots are decomposed, no production Rust file exceeds 1,500 lines, thin entry modules and compatibility re-exports are in place, and existing golden results, traces and artifact schemas are unchanged.

GATE 02

Build provenance

Every target’s required firmware is compiled in a pinned Docker toolchain with networking disabled, and the result records source, flags, compiler identity and artifact hashes.

GATE 03

CPU and ABI

Each target passes its instruction vectors and compiler corpus at the documented optimization levels, including startup, calls, stack, arithmetic helpers, native type widths and interrupt prologues.

GATE 04

Machine behaviour

Each exact chip boots from its documented reset state, initializes memory, configures clocks sufficiently, services a timer interrupt, reads externally stimulated GPIO and transmits through its selected UART.

GATE 05

Waveform observability

Each chip produces a valid VCD containing stable hierarchical GPIO, UART and selected timer/interrupt signals. Assertions verify edge order and repeated runs yield identical event digests.

GATE 06

Vendor evidence

At least one selected official vendor example per chip runs with its peripheral source logic unchanged. The RA4M1 additionally runs pinned ArduinoCore-renesas Blink and HardwareSerial sketches. Linker/startup adaptation and a host-side test harness are allowed only when documented.

GATE 07

Regression and honesty

The original six targets still pass their required gate. New register coverage, fidelity and unsupported behaviour are published, and no unimplemented block is represented as hardware-accurate.

GATE 08

Portfolio completion

All seven expansion targets pass independently in one comprehensive command. Seven names backed by shared stubs do not count; every target must demonstrate its own CPU profile, image format, memory map, interrupt routing and peripheral trace.

Completion command

The final repository documents one stable command that builds or verifies toolchain images, runs the complete qualification matrix and emits a machine-readable summary. The exact command may evolve during implementation; its seven-target semantics may not.
