01

Mission and completion rule

Primary objective

Run the exact firmware bytes published by MicroPython for M5Stack NanoC6, M5Stack AtomS3 Lite, Raspberry Pi Pico, and Raspberry Pi Pico 2 from realistic reset state through their normal boot path.

Development builds are permitted for symbols and diagnosis. They never count as final evidence.

Final statement we earn

“The official MicroPython release boots and behaves correctly across the four target boards, including both official RP2350 CPU modes, under a deterministic and observable simulation.”

This is strong evidence of CPU, ABI, exceptions, interrupts, memory, flash, timers, I/O and system integration. It is not a claim of electrical or cycle-accurate silicon equivalence.

Boards 4

All mandatory.

CPU profiles 5

RP2350 Arm and RISC-V both qualify.

Firmware policy 0 patches

Official bytes remain unchanged.

Unexpected skips 0

At the final release gate.

Interpretation of “all four cores”

The required portfolio is the four named board targets. Pico 2 additionally ships official Cortex-M33 and Hazard3/RISC-V firmware, so both are separate mandatory execution profiles. Secondary physical cores are brought into scope wherever the official firmware exposes them through _thread, SDK services, or inter-core coordination.

Official-image rule

Final tests download from micropython.org, verify a committed SHA-256 manifest, decode the container format into simulated non-volatile storage, and reset the machine. ESP ELF/map companions may label traces, but execution must come from the official flash image. Pico ELF files generated in development containers are diagnostic aids only.

03

Qualification rules

Permitted during development
  • Symbol-rich source builds from the same MicroPython tag
  • Frozen diagnostic scripts
  • Single-step, register and MMIO traces
  • Hardware record/replay and fault injection
  • Temporary assertions in Renvo
Forbidden as final evidence
  • Patched firmware or altered SDK configuration
  • Direct jump to main or mp_task
  • Test-only MMIO escape devices
  • Replacing USB with a private UART console
  • Skipping a failure because “the REPL works”
Allowed silicon boundary
  • Audited mask-ROM services where ROM bytes cannot be distributed
  • Deterministic host-backed physical environments
  • Functional rather than RF/electrical fidelity
  • Approximate timing with documented ordering
  • Explicit model-version metadata
No success-by-stubbing

A ROM façade may implement a documented silicon service at the mask-ROM boundary. A façade may not recognize MicroPython code, forge peripheral status to advance a known boot, return canned Python output, or bypass the guest’s own interrupt, scheduler, filesystem, networking, or protocol logic.

05

Target-specific closure

RP2040 · Pico

First complete vertical slice

  • Complete the Cortex-M0+ ISA, exception return, PPB, NVIC and system control surface used by pico-sdk.
  • Decode UF2 into external flash, model boot ROM/boot2, SSI/XIP, clocks, PLLs and resets.
  • Implement SIO, IO_BANK0, PADS_BANK0, TIMER alarms, watchdog tick, RTC source and random/unique-ID contracts.
  • Add USB device/CDC, UART, I²C, SPI, PWM, ADC, DMA and PIO behavior used by the RP2 port.
  • Implement core 1, spinlocks, FIFO and deterministic _thread scheduling.
Exit: official Pico UF2 cold-boots, enumerates as USB CDC, accepts raw REPL tests, persists files, and passes the RP2040 board suite.
RP2350 · Pico 2

One chip, two mandatory architectures

  • Bring Cortex-M33 non-secure execution to the compiler/exception/DSP/FPU surface exercised by official firmware.
  • Complete Hazard3 RV32IMAC and bit-manipulation, privilege, interrupt and atomic behavior used by the RISC-V release.
  • Model RP2350 boot selection, QMI/XIP, clocks/resets/power state, SIO, timers, DMA, PIO and USB.
  • Share peripheral state between CPU profiles without sharing architecture-specific interrupt or reset assumptions.
  • Run identical high-level Python tests and compare only behavior that should be architecture-independent.
Exit: both official Pico 2 UF2 variants independently cold-boot and pass the same applicable board suite, including multicore tests.
ESP32-C6 · NanoC6

ESP-IDF and FreeRTOS on RISC-V

  • Complete ESP RISC-V privilege, CSR, PMP-visible, exception, interrupt and atomic behavior required by IDF.
  • Parse the combined ESP image and model ROM boot services, second-stage bootloader, partition table, cache and mapped flash.
  • Implement system/reset/clock/power controls, documented interrupt routing, SYSTIMER/TIMG, watchdogs and FreeRTOS tick sources.
  • Add GPIO/IO MUX, USB Serial/JTAG, UART, GDMA, I²C, SPI, ADC, LEDC/RMT, eFuse/unique-ID and deterministic RNG models.
  • Provide functional Wi-Fi/BLE virtual peers and persistent NVS/filesystem behavior.
  • Use the existing NanoC6 safely as a register/reset/output oracle; preserve its factory-flash backup.
Exit: official NanoC6 combined BIN boots through the IDF chain, reaches its normal console, and passes ESP32-C6 runtime/peripheral/connectivity suites.
ESP32-S3 · AtomS3 Lite

Xtensa is the final CPU closure

  • Implement LX7 register windows, window overflow/underflow, loop instructions, atomics, exceptions, interrupt levels, barriers and FPU operations used by IDF.
  • Model dual-core reset/start coordination and deterministic FreeRTOS scheduling when the official build uses the second core.
  • Parse official UF2/BIN, implement ROM/bootloader, cache/MMU and IRAM/DRAM/IROM/DROM behavior without PSRAM assumptions.
  • Add system/clock/reset, interrupt matrix, timers, watchdogs, GPIO matrix/IO MUX, USB, UART, GDMA, I²C, SPI, ADC, LEDC/RMT and flash/NVS.
  • Model the board button and addressable RGB path, then apply the shared ESP Wi-Fi/BLE environment.
Exit: official AtomS3 Lite firmware cold-boots, reaches USB/serial REPL, and passes the ESP32-S3 board suite including windowed-ABI stress.

Container and artifact discipline

Renvo executes on the host, but every compiler, SDK, firmware source build, test controller and conversion tool runs in a pinned Docker image. Official release firmware is downloaded, hashed and archived; it is not rebuilt for final acceptance.

Container Contents Purpose
renvo/micropython-rp2 Pinned MicroPython tag/submodules, pico-sdk, Arm and Hazard3 compilers, CMake/Ninja, mpy-cross, picotool/UF2 tools. Symbol-rich Pico/Pico2 builds, frozen probes, ELF/map extraction and native-emitter fixtures.
renvo/micropython-esp32 Pinned MicroPython tag, matching ESP-IDF revision/submodules, Espressif RISC-V/Xtensa tools and esptool. Diagnostic NanoC6/AtomS3 builds, maps, partition inspection and hardware-oracle utilities.
renvo/micropython-tests Pinned upstream test tree, CPython controller, pyboard transport adapter, VCD/protocol validators. Runs the same test selection against every virtual board without host Python drift.
renvo/mquickjs Pinned upstream commit, native build tools and all embedded cross-compilers. Builds ROM-embedded 32-bit JavaScript workloads for every CPU profile.
renvo/firmware-fetch Minimal TLS/downloader, SHA-256, manifest validator and archive unpackers. Fetches official release artifacts once; final CI consumes the content-addressed cache offline.
Build isolation

No network after image construction, read-only source mounts, dedicated output volume, dropped capabilities, bounded CPU/RAM/PIDs.

Provenance

OCI digest, source commit/tag, submodule revisions, command line, environment, input and output hashes in one JSON manifest.

End-to-end implementation roadmap

Freeze evidence and build the qualification harness

Foundation
  • Commit official v1.28.0 URLs, filenames, SHA-256 values, release date, board IDs and RP2350 CPU-mode metadata.
  • Add UF2 and ESP combined-image parsing, persistent flash snapshots and corruption tests.
  • Add virtual serial/USB endpoints, a transport compatible with upstream raw REPL tooling, and structured test results.
  • Add unknown-MMIO diagnostics, register coverage, IRQ provenance, checkpoints and deterministic replay digests.
  • Build the five pinned Docker images and offline artifact cache.
Gate: every official image verifies and maps reproducibly; a synthetic USB/serial guest can be driven through the same host test transport.

RP2040 official boot to first prompt

First vertical
  • Close Cortex-M0+ instruction and exception gaps using pico-sdk and MicroPython diagnostic ELFs.
  • Implement reset-to-ROM, boot2, external flash/XIP, clocks/resets, timer/watchdog and NVIC.
  • Implement enough USB CDC and flash filesystem behavior to see the normal banner and prompt.
  • Run one raw-REPL arithmetic script and a machine.Pin VCD blink from the official UF2.
Gate: a pristine flash snapshot cold-boots the official Pico UF2 and executes an externally supplied Python script through its native USB REPL.

Complete the RP2040 MicroPython surface

Deepen
  • Implement bidirectional UART, GPIO IRQ/pulls/open-drain, PWM, ADC, I²C, SPI, DMA and PIO.
  • Add core 1, SIO synchronization, _thread, WFI wakeups and deterministic multicore ordering.
  • Pass upstream language/runtime tests, native/viper emitter tests and the board peripheral suite.
  • Qualify filesystem persistence, soft reset, power cycle, watchdog and USB reconnect.
Gate: Pico passes the complete acceptance suite with no Renvo-specific skips and becomes the reference implementation for shared RP devices.

RP2350 in Arm and RISC-V modes

Dual profile
  • Close Cortex-M33 and Hazard3 ISA/exception/interrupt/atomic gaps independently.
  • Add RP2350 reset/boot, QMI/XIP and peripheral differences without aliasing RP2040 registers blindly.
  • Boot both official UF2 artifacts and run the same applicable tests through USB raw REPL.
  • Compare architecture-independent Python output, protocol traffic and waveform semantics across modes.
Gate: both official Pico 2 firmware variants pass; a failure in one mode cannot be hidden by the other.

ESP32-C6 and the NanoC6 hardware oracle

ESP first
  • Close ESP RISC-V, privilege, PMP-visible, interrupt and atomic behavior against IDF-generated code.
  • Implement ROM/bootloader/partition/cache path, FreeRTOS timing, flash/NVS and the normal console transport.
  • Use safe RAM/JTAG probes and restored flash images to compare reset values, IRQ routing and peripheral transcripts with the physical NanoC6.
  • Add ESP peripheral and functional Wi-Fi/BLE virtual-environment tests.
Gate: official NanoC6 BIN cold-boots and passes the comprehensive ESP32-C6 suite; hardware-comparable cases agree within documented functional timing bounds.

ESP32-S3 / AtomS3 Lite

Xtensa closure
  • Complete the LX7 windowed ABI, exceptions, atomics, interrupt levels and FPU from focused tests before entering IDF.
  • Implement S3 ROM/boot/cache/MMU, dual-core coordination and the official board’s no-PSRAM memory layout.
  • Reuse behavior-level ESP devices while keeping S3/C6 register maps and interrupt wiring distinct.
  • Qualify USB/serial, storage, machine peripherals, RGB/button, networking, BLE and applicable threads.
Gate: official AtomS3 Lite UF2/BIN boots normally and passes the comprehensive ESP32-S3 suite.

Cross-runtime qualification with MQuickJS

Independent proof
  • Build a small board shim in the existing Docker toolchains and embed upstream MQuickJS tests as ROM bytecode/source.
  • Run parser, VM, compacting GC, UTF-8, regexp, integer, double/soft-float, typed-array and memory-limit stress.
  • Run identical deterministic JavaScript workloads on all five CPU profiles and compare canonical results.
  • Keep this workload independent of MicroPython internals and test escape devices.
Gate: all five profiles pass the pinned MQuickJS suite and seeded CPU/ABI faults are detected by at least one independent runtime.

Official-firmware release qualification

Final
  • Start each run from a clean, erased-or-fixtured flash image and hardware reset state.
  • Run the full upstream and board suites, repeated determinism runs, persistent-state scenarios and negative tests.
  • Generate per-board support/coverage manifests and fail on unknown MMIO, unexpected skip, nondeterminism or undocumented approximation.
  • Archive content-addressed evidence and publish one four-board qualification report.
Gate: every requirement in §10 is green in one reproducible invocation using only official firmware artifacts.

Test ladder

Level Scope Pass condition
L0 · Component Instruction semantics, memory, MMIO registers, FIFOs, IRQs, USB packets, buses, flash rules and scheduler ordering. Exhaustive/table/property tests pass; errors identify exact opcode/register/event.
L1 · Diagnostic firmware Container-built, symbol-rich probes and focused SDK programs. Expected state/transcript/VCD; no unknown MMIO; hardware comparison where available.
L2 · Official boot Exact stable image from reset through normal boot and console enumeration. Expected MicroPython identity/banner and raw REPL round trip without guest patching.
L3 · Runtime Upstream MicroPython language, compiler, bytecode, GC, exception, import, native/viper and stress tests applicable to the official build. Upstream expected outcomes; no Renvo-only skip list or flaky retries.
L4 · Machine APIs Pin/IRQ, Timer, PWM, ADC, UART, I²C, SPI, RTC, WDT, unique ID, frequency control, sleep/reset, PIO/RMT/DMA and threads where exposed. Python result, protocol transcript, IRQ sequence and waveform assertions all agree.
L5 · System USB disconnect/reconnect, filesystem persistence/recovery, soft reset, power cycle, contention/errors, multicore and ESP virtual connectivity. Correct recovery and reset causes; no deadlock; bounded completion.
L6 · Independent runtime Pinned MQuickJS embedded suite on every CPU profile. Canonical JavaScript results and memory limits match reference.
L7 · Determinism Repeat every final scenario with trace perturbations disabled/enabled and on supported host platforms. Same semantic result, event digest and protocol/VCD sequence; no wall-clock dependence.

Upstream test policy

The suite may honor skips already made by upstream for that MicroPython port/build and tests requiring physically absent hardware. Renvo may not add emulator-specific skips. A physics-dependent feature included by the official firmware must receive a deterministic functional environment or remain a release-blocking gap.

09

MQuickJS as the independent workload

Why it is valuable

MicroPython and its vendor ports can repeatedly exercise the same compiler and runtime patterns. MQuickJS adds a different C codebase, parser, bytecode VM, compacting garbage collector, UTF-8/string implementation, regexp engine, typed arrays and math implementation.

It is designed for embedded systems, can run in roughly 10 KiB of RAM, requires little libc support, accepts a caller-supplied heap, and can execute 32-bit persistent bytecode from ROM.

How Renvo will use it
  • Pin an exact upstream commit and retain its MIT license/provenance.
  • Compile per CPU profile in the same Docker toolchains used for firmware probes.
  • Embed scripts and expected canonical output; use normal UART and board timer/GPIO shims.
  • Exercise hardware float where available and the project’s software floating-point path elsewhere.
  • Run upstream basic tests, microbench kernels and targeted allocator/GC limits.
Position in the project

MQuickJS is a required independent CPU/ABI/runtime cross-check, not a replacement firmware target and not a reason to postpone MicroPython peripheral work. Official MicroPython remains the final compatibility claim.

Final acceptance contract

Single release gate

One offline command starts from the pinned official artifacts and a clean content-addressed environment, executes every profile below, and exits successfully only if every mandatory assertion passes.

Required run Firmware origin Mandatory final evidence
Pico / RP2040 Official v1.28.0 UF2 Cold boot, USB raw REPL, upstream suite, full RP board suite, threads, storage, VCD and repeat digest.
Pico 2 / Cortex-M33 Official v1.28.0 UF2 Same, with RP2350/Arm-specific native, exception, multicore and peripheral coverage.
Pico 2 / Hazard3 Official v1.28.0 RISC-V UF2 Same high-level suite plus RISC-V native/interrupt/atomic coverage and cross-mode semantic comparison.
NanoC6 / ESP32-C6 Official v1.28.0 combined BIN ROM/bootloader boot, normal console, upstream suite, ESP board suite, NVS/storage, virtual Wi-Fi/BLE, VCD and hardware-oracle comparison subset.
AtomS3 Lite / ESP32-S3 Official v1.28.0 UF2/BIN ROM/bootloader boot, normal console, upstream suite, ESP board suite, Xtensa windows/FPU/IRQs, dual-core where used, connectivity, VCD and repeat digest.

The gate fails if any of these is true

  • An official artifact hash is unknown or different
  • Execution begins after the normal hardware boot boundary
  • A firmware byte, partition or configuration is patched
  • USB/serial behavior is replaced by a private guest interface
  • An upstream-applicable test fails or receives a Renvo-only skip
  • A mandatory board API lacks a deterministic test environment
  • An unknown MMIO access or unhandled interrupt occurs
  • A test completes only because of a MicroPython-aware stub
  • Repeated runs differ semantically or in ordered event digest
  • Trace/VCD/protocol assertions disagree with Python-visible state
  • Persistent storage fails across soft reset or power cycle
  • Any of the five execution profiles is missing
Per-run bundle

Firmware hash, flash before/after, machine manifest, transcript, test results, event digest, VCD, protocol logs, MMIO/IRQ coverage and timing statistics.

Portfolio report

Five profiles, pass counts, upstream skips, register coverage, known functional approximations, Docker digests and source links.

Confidence claim

Strong functional confidence for documented, tested behavior; no claim of cycle, analog, RF, security side-channel or undocumented silicon-quirk fidelity.

Primary risks and controls

Risk Control Warning sign
“Boots” is mistaken for “works” Layered runtime, machine, protocol, persistence, multicore and determinism gates. The milestone is declared complete at the first REPL prompt.
Official image is too opaque to debug Reproduce the same tag in containers for ELF/map symbols, then confirm every fix against untouched official bytes. A fix only works in the development build.
ROM façade becomes application emulation Versioned, sourced ROM API boundary with unit tests and call tracing; ban caller-specific results. The façade checks the guest PC or MicroPython symbol.
USB consumes the project Packet-level functional model, CDC first, reusable host controller, strict endpoint coverage ledger. Device enumeration relies on hard-coded descriptor responses.
ESP-IDF dependency explosion Fault-guided closure from boot, shared behavior models with distinct register adapters, and explicit phase gates. Large permissive register banks silently accept accesses.
Wireless becomes RF simulation Functional virtual AP/BLE peer at controller/environment boundary; document timing and RF omissions. Work begins on modulation or antenna behavior.
Multicore loses determinism Single host-thread scheduler, explicit quanta, stable same-time ordering, checkpoints and replay digests. Results depend on host thread scheduling.
RP2040 behavior copied into RP2350 Separate manifests/register adapters and tests derived from each datasheet. Pico 2 passes only through undocumented RP2040 aliases.
Xtensa gaps are masked by call0 tests Windowed-ABI corpus, exceptions, interrupts and official ESP-IDF firmware are mandatory. Compiler corpus passes but IDF fails immediately on a window instruction.
Test suite overfits MicroPython MQuickJS, existing 1,000-case C corpus and focused ISA suites stay independent. A CPU bug affects other binaries but not the Python runtime.
Latest release moves during development Locked v1.28.0 gate plus non-blocking rolling stable lane and deliberate baseline updates. CI silently downloads a different artifact under the same job.
Current six-chip work is discarded Retain CH32/compiler corpus as regression coverage; focus new implementation milestones on the four MicroPython boards. Shared CPU/device changes regress existing tests unnoticed.

Ordered work queue

  1. Official artifact manifest: download v1.28.0 files, record hashes, formats, board IDs and licence/source references.
  2. UF2 loader: validate family IDs, ordering, duplication, address bounds and flash placement for RP and AtomS3 artifacts.
  3. ESP image loader: parse combined image, bootloader, partition table, app segments/checksums and mapped flash.

  5. Qualification transport: virtual serial and USB host endpoints compatible with raw REPL tooling.
  6. Coverage diagnostics: unknown MMIO faults, register bitmap, IRQ provenance, boot checkpoints and bounded trace bundles.
  7. RP2040 CPU closure: run pico-sdk/MicroPython diagnostic ELF until no compiler/exception gap remains.
  8. RP2040 reset/XIP: boot ROM contract, boot2, SSI flash, aliases, clocks, resets, timer/watchdog and NVIC.
  9. RP2040 USB/repl: enumerate official UF2 and execute the first external raw-REPL script.
  10. RP peripherals: full GPIO/pads/IRQ, UART, I²C, SPI, PWM, ADC, DMA and PIO test slices.
  11. RP multicore: core launch, FIFO, spinlocks, memory ordering and deterministic _thread.
  12. RP2040 comprehensive gate: make Pico the first fully green board.
  13. RP2350 Arm: Cortex-M33, boot/QMI and RP2350-specific peripherals through official UF2.
  14. RP2350 RISC-V: Hazard3 and interrupt model through official RISC-V UF2.
  15. ESP32-C6 CPU/boot: IDF instruction/privilege closure, ROM, bootloader, partitions, cache, timers and interrupts.
  16. NanoC6 system: console, flash/NVS, GPIO, UART/USB, buses, DMA, analog/PWM/RMT and safe hardware comparisons.
  17. ESP virtual connectivity: deterministic AP/network and BLE peer with contained packet services.
  18. Xtensa LX7 closure: windows, exceptions, atomics, interrupt levels, FPU and IDF ABI.
  19. AtomS3 system: boot/cache/MMU, dual core, USB, flash/NVS, peripherals, RGB/button and connectivity.
